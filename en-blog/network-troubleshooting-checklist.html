Network Troubleshooting Checklist: DNS, DHCP, VLAN and Connectivity

When someone reports that “the internet is down,” the internet may not be the problem. The failure can be a cable, switch port, VLAN, DHCP scope, gateway, DNS resolver, firewall policy or a single service. Professional troubleshooting starts with the lowest layer and uses a measurable test at every step.

1. Define the scope

  • One user or many?
  • One VLAN or the whole network?
  • Internal connectivity or internet only?
  • Constant or intermittent?

2. Check the physical and link layer

Check the NIC and switch-port link, cable, patch panel and port status. If possible, test a known-good client on the same port. The goal is to separate physical failures from logical ones.

3. Validate IP configuration and gateway

ipconfig /all
ping 127.0.0.1
ping <default-gateway>

If the client has no valid address, investigate DHCP. If the gateway cannot be reached, inspect VLAN membership, ARP, switching and local ACLs before touching DNS.

4. Isolate DNS

nslookup example.com
nslookup example.com <dns-server>

If connectivity to an IP works but name resolution fails, DNS is a much stronger suspect than the internet connection itself.

5. Check VLAN and DHCP

Confirm that the access port belongs to the intended VLAN, trunks allow that VLAN, and the corresponding DHCP scope is active and has capacity. See VLAN Segmentation and DHCP Snooping and DAI.

6. Check routing and firewall policy

tracert 1.1.1.1
ping 1.1.1.1

If the gateway is healthy but external destinations fail, inspect routing, NAT, firewall policies, VPN paths and the upstream connection. Change one variable at a time and document the result.

7. Consider security signals

Unexpected DHCP, unusual ARP behavior or sudden traffic changes can indicate a security problem. Preserve switch, DHCP, DNS and firewall logs before making destructive changes. For hardening guidance, see Network Hardening and Active Directory Hardening.

8. The troubleshooting rule that saves time

Test one hypothesis at a time. Record the result, eliminate or confirm the hypothesis, and only then move to the next layer. This is faster and leaves you with a reproducible troubleshooting trail.
