DNS troubleshooting in an enterprise network: from name to response

A practical workflow for cases where systems have IP connectivity but names do not resolve correctly.

1. Define the problem first

Determine whether the problem affects one client or the entire network. Test from the affected client using both an internal name and a public name. This helps separate client, DNS server, zone and resolver-path problems.

2. Check the client's DNS configuration

On Windows, use ipconfig /all. On Linux, use your network manager tools or resolvectl status. Confirm exactly which DNS servers the client is using. Unrelated DNS servers can produce inconsistent answers and unpredictable behavior.

3. Test with nslookup or dig

nslookup server.example.local
nslookup example.com 8.8.8.8
dig server.example.local

If an internal resolver answers but a public resolver does not, check the internal record or split-DNS design. If no resolver answers, investigate network reachability, the DNS service and firewall rules.

4. Check records and zones

Verify A, AAAA, CNAME and related records. For enterprise services, also consider TTL and caching. A record change does not necessarily become visible to every client immediately.

5. Do not flush cache blindly

Flushing cache can help, but it should not replace diagnosis. Record the query result and the DNS server being used before clearing caches so the original behavior can be reproduced.

6. If you use Active Directory

In AD environments, DNS is part of authentication and service discovery. Client and domain-controller DNS settings must match the AD architecture. DNS failures can appear as login, Group Policy or service-discovery problems.

Quick checklist

  • Correct DNS servers configured on the client.
  • Network access to DNS port 53.
  • Correct zone and records.
  • Difference between internal and public responses understood.
  • Cache and TTL considered.
  • DNS server logs reviewed.
  • For AD, DNS health and service records checked.
