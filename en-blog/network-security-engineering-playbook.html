Network Security Engineering Playbook: Architecture to Monitoring

Network security is not a single product. It is an engineered system of architecture, access control, hardening, visibility, recovery and continuous validation. This playbook turns those ideas into a practical workflow for real environments.

Author: Mohammad Hossein Asgari SomarinLevel: Intermediate to AdvancedUpdated: September 15, 2026

1. Start with assets and communication paths

Before changing a firewall rule or deploying another security product, establish what you are protecting. Inventory users, servers, network devices, management interfaces, critical services, VLANs, subnets, Internet paths and privileged accounts. The output should be a simple architecture map that can be maintained.

For each critical service record its owner, location, dependencies, required ports, sensitivity, backup method and administrative path. This creates both a security baseline and a troubleshooting baseline.

2. Design segmentation around risk

Users, servers, management interfaces, cameras and guest devices do not need to share the same trust boundary. VLANs and routing policies should reflect role and risk rather than only physical location.

  • Client VLAN for standard users
  • Server VLAN for infrastructure services
  • Management VLAN for administrative interfaces
  • Voice, CCTV and IoT VLANs for specialized devices
  • Guest VLAN with Internet-only access where appropriate

Inter-VLAN access should be explicit. Define required flows and deny unnecessary communication. Segmentation becomes much more valuable when the firewall and ACL policy matches the intended trust model.

3. Harden the access layer

Security does not begin at the perimeter firewall. DHCP Snooping can reduce exposure to rogue DHCP servers, while Dynamic ARP Inspection can help defend against ARP spoofing when its bindings and trusted ports are correctly designed. Port security, unused-port shutdown and restricted management access provide additional layers.

Do not enable security features blindly. Validate switch capabilities, trusted paths and failure modes, then make changes in small, reversible steps.

4. Build firewall policy around real flows

Every important firewall rule should have an understandable reason: source, destination, service, business purpose, owner and review date. Periodically review stale objects, unused rules and broad Any/Any access.

On FortiGate or another enterprise firewall, logging should be enabled for security-relevant flows. Review policy hit counts and logs before removing or changing rules. A secure policy is one that is both restrictive and operationally understood.

5. Protect identity and management planes

Administrative accounts should be separated from everyday user accounts. Where supported, use MFA, restrict management access by source network, use secure protocols and limit exposure of management interfaces.

In Active Directory environments, review privileged group membership, service accounts, sensitive GPOs and authentication events. Least privilege should be a recurring review process, not a one-time configuration task.

6. Turn logs into monitoring

Collecting logs is not the same as monitoring. Define the questions that matter: What is an unusual authentication pattern? Which firewall change should trigger an alert? When should a DNS change be investigated? Which traffic or interface behavior is abnormal?

Baseline availability, packet loss, latency, interface errors, CPU and memory, disk capacity and backup status. For security, prioritize privileged changes, authentication failures, firewall changes and unusual network behavior.

7. Prepare incident response before the incident

A short runbook can reduce confusion under pressure: detect, contain, preserve evidence, eradicate the cause, recover, validate and document lessons learned. Avoid destroying useful evidence simply to make a system appear healthy again.

The goal is not only to restore connectivity. A mature response asks why the existing controls failed and what change will reduce recurrence.

8. Treat backup and recovery as security controls

A backup that has never been restored is an assumption. Protect configuration backups for firewalls, switches and servers, restrict access, retain appropriate versions and test recovery. Exercise realistic failure scenarios instead of relying only on successful backup jobs.

9. Create a continuous improvement loop

  1. Document the current baseline.
  2. Prioritize the highest-impact risks.
  3. Implement one controlled and reversible change.
  4. Validate the result with monitoring, logs and functional tests.
  5. Update documentation.
  6. Review again on a defined schedule.

This turns security from a pile of settings into an engineering process that can be measured, reviewed and improved.

Rapid assessment checklist

  • Assets and communication paths are documented.
  • VLANs and ACLs reflect roles and risk.
  • Management interfaces are restricted.
  • Layer 2 protections are reviewed.
  • Broad and stale firewall rules are reviewed.
  • Security-relevant logging and alerting are active.
  • Privileged and service accounts are reviewed.
  • Backup restoration has been tested.
  • Incident response and escalation paths are documented.
