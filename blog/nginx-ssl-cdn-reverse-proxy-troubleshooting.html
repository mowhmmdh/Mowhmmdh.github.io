عیب‌یابی خطای SSL پشت CDN و Reverse Proxy؛ چک‌لیست عملی Nginx

وقتی سایت با خاموش‌کردن Proxy باز می‌شود اما با فعال‌کردن CDN خطایی مثل ERR_SSL_VERSION_OR_CIPHER_MISMATCH می‌دهد، باید مسیر TLS را لایه‌به‌لایه بررسی کرد؛ نه اینکه فوراً گواهی را دوباره نصب کنیم.

نویسنده: محمدحسین عسگری ثمرین · آخرین بازبینی: ۱۱ اکتبر ۲۰۲۶ · زمان مطالعه: حدود ۷ دقیقه

۱. اول مشخص کن TLS کجا قطع می‌شود

در معماری معمول مرورگر ← CDN ← سرور مبدا دو اتصال مستقل TLS وجود دارد: یکی بین کاربر و CDN و دیگری بین CDN و Origin. موفق‌بودن اتصال مستقیم به Origin ثابت نمی‌کند اتصال کاربر به CDN هم سالم است؛ همین‌طور گواهی معتبر روی Origin به‌تنهایی تنظیمات SSL در پنل CDN را تضمین نمی‌کند.

اصل عیب‌یابی: هر بار فقط یک بخش را تغییر بده و قبل و بعد از تغییر، خروجی قابل مقایسه بگیر.

۲. رکورد DNS و مقصد واقعی را بررسی کن

ابتدا بررسی کن نام دامنه به مقصد مورد انتظار اشاره می‌کند و رکوردهای قدیمی یا متناقض وجود ندارند.

dig +short example.com
dig +short www.example.com
curl -sS -D- -o /dev/null https://example.com/

وقتی Proxy روشن است، IPهای پاسخ‌داده‌شده ممکن است متعلق به CDN باشند؛ این موضوع به‌خودی‌خود خطا نیست. برای بررسی Origin از شبکه مجاز خودت استفاده کن و IP عمومی سرور را بی‌دلیل در معرض دسترسی قرار نده.

۳. اتصال مستقیم به Origin را با SNI تست کن

این تست، درخواست را به IP انتخابی می‌فرستد اما نام دامنه را برای TLS و HTTP حفظ می‌کند:

curl -vkI --resolve example.com:443:ORIGIN_IP https://example.com/

برای تست گواهی و زنجیره TLS، گزینه -k را حذف کن؛ چون -k خطاهای اعتبارسنجی گواهی را پنهان می‌کند. از خروجی تست بدون -k برای بررسی نام دامنه، تاریخ اعتبار و اعتماد زنجیره استفاده کن.

openssl s_client -connect ORIGIN_IP:443 -servername example.com -showcerts

اگر این تست موفق است، به سراغ تنظیمات SSL/TLS و گواهی سمت CDN برو. اگر شکست می‌خورد، ابتدا Virtual Host، پورت ۴۴۳، SNI، فایروال و گواهی Origin را بررسی کن.

۴. پیکربندی Nginx و گواهی را اعتبارسنجی کن

sudo nginx -t
sudo nginx -T
sudo ss -lntp | grep ':443'
sudo systemctl status nginx --no-pager
sudo journalctl -u nginx --since "30 minutes ago" --no-pager
  • برای هر دامنه، server_name درست تعریف شده باشد.
  • مسیر ssl_certificate به گواهی مناسب و زنجیره کامل اشاره کند.
  • کلید خصوصی با گواهی متناظر باشد و مجوز فایل‌ها امن بماند.
  • فایل‌های تکراری در sites-enabled یا نام دامنه اشتباه، Virtual Host ناخواسته نسازند.
  • پس از تغییر، ابتدا nginx -t و فقط در صورت موفقیت reload اجرا شود.
sudo nginx -t && sudo systemctl reload nginx

۵. حالت SSL در CDN را با Origin هماهنگ کن

در پنل CDN بررسی کن گواهی لبه (Edge Certificate) فعال و برای دامنه درست صادر شده باشد. اگر اتصال CDN به Origin باید HTTPS باشد، گواهی Origin باید از دید CDN قابل اعتبارسنجی باشد و نام دامنه مورد انتظار را پوشش دهد. حالت‌های رمزنگاری و گزینه‌های بررسی گواهی را بر اساس مستندات همان CDN تنظیم کن؛ کاهش امنیت یا غیرفعال‌کردن اعتبارسنجی را راه‌حل دائمی قرار نده.

اگر گواهی لبه فعال نیست، ممکن است خطا پیش از رسیدن درخواست به Nginx رخ دهد. در آن حالت، تغییرات سمت Origin الزاماً مشکل را حل نمی‌کند.

۶. لاگ‌ها را هم‌زمان با یک درخواست واقعی بخوان

sudo tail -f /var/log/nginx/error.log
sudo tail -f /var/log/nginx/access.log

در یک ترمینال لاگ‌ها را باز بگذار و در ترمینال دیگر فقط یک درخواست کنترل‌شده بفرست. اگر هیچ درخواستی در Origin ثبت نمی‌شود، احتمال دارد خطا در DNS، اتصال کاربر به CDN یا TLS لبه رخ دهد. اگر درخواست به Origin می‌رسد، timestamp و خطای متناظر را دنبال کن.

چک‌لیست نهایی

  1. DNS و وضعیت Proxy را ثبت کن.
  2. Edge TLS و گواهی دامنه را در CDN بررسی کن.
  3. Origin را با curl --resolve و SNI تست کن.
  4. اعتبار گواهی را بدون -k بررسی کن.
  5. nginx -t، nginx -T و لاگ‌ها را بخوان.
  6. هر بار یک تغییر انجام بده، دوباره تست کن و نتیجه را مستند کن.

برای ایمنی، IPهای Origin و خروجی‌های دارای اطلاعات حساس را در گزارش عمومی منتشر نکن. اگر مشکل ادامه دارد، زمان خطا، نام CDN، خطای دقیق مرورگر و نتیجه تست TLS را جمع‌آوری کن؛ کلید خصوصی یا توکن‌ها را ارسال نکن.
