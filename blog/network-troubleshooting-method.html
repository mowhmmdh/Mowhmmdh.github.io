روش مهندسی عیب‌یابی شبکه: Evidence → Hypothesis → Test

عیب‌یابی حرفه‌ای با تغییر تنظیمات شروع نمی‌شود؛ با تعریف دقیق مسئله، جمع‌آوری Evidence و ساختن یک Baseline قابل اندازه‌گیری شروع می‌شود. هدف این روش این است که از تغییرات تصادفی جلوگیری شود و هر تصمیم فنی قابل توضیح و قابل تکرار باشد.

Pipeline: Symptom → Scope → Baseline → Evidence → Hypothesis → Controlled Test → Root Cause → Fix → Validation → Documentation

۱. Scope را مشخص کنید

اول مشخص کنید مشکل برای چه کاربران، سرویس‌ها، VLANها، مقصدها و بازه زمانی رخ می‌دهد. مشخص کردن Scope کمک می‌کند مشکل سراسری را از یک اختلال نقطه‌ای جدا کنید. زمان شروع، تعداد کاربران متاثر، سرویس‌های درگیر و تغییرات اخیر را ثبت کنید.

۲. Baseline بگیرید

Latency، packet loss، DNS response time، interface errors، CPU، memory، وضعیت route و health سرویس را با زمان ثبت کنید. یک ping موفق به‌تنهایی سلامت شبکه را ثابت نمی‌کند؛ باید مسیر و لایه‌های مرتبط را هم بررسی کرد.

۳. Evidence جمع کنید

از لاگ‌ها، counters، وضعیت interface، جدول‌های routing و ARP، DNS lookup، trace مسیر و telemetry موجود استفاده کنید. Evidence باید تا حد امکان timestamp داشته باشد تا بتوان رخدادها را با یکدیگر تطبیق داد.

۴. Hypothesis بسازید

هر فرضیه باید قابل آزمایش باشد؛ برای مثال DNS latency، route asymmetry، congestion، packet loss، MTU یا service-side latency. برای هر فرضیه یک تست مشخص تعریف کنید و قبل از تغییر production، نتیجه مورد انتظار را بنویسید.

۵. تست کنترل‌شده انجام دهید

اگر تغییر لازم شد، فقط یک متغیر را تغییر دهید. محدوده اثر، زمان اجرا و معیار موفقیت را مشخص کنید. اگر نتیجه با فرضیه سازگار نبود، به جای انباشتن تغییرات، فرضیه را رد کنید و سراغ شواهد بعدی بروید.

۶. Root Cause را از Symptom جدا کنید

رفع موقت symptom لزوماً Root Cause نیست. بعد از اصلاح، همان Evidence اولیه را دوباره اندازه‌گیری کنید. اگر latency، loss، error یا service health به وضعیت مورد انتظار برگشته است، آن را با baseline مقایسه کنید.

۷. Validation و Rollback

Validation باید شامل تست عملکرد، بررسی لاگ، بررسی اثر جانبی و تایید کاربر یا سرویس باشد. برای تغییرات حساس، rollback باید قبل از اجرا تعریف شده باشد؛ تغییر بدون مسیر بازگشت ریسک عملیاتی را بالا می‌برد.

۸. مستندسازی قابل تکرار

Timeline، Evidence، Hypothesis، Change، Result و Lesson Learned را ثبت کنید. این مستندات در Incident بعدی به‌عنوان Runbook اولیه عمل می‌کنند و وابستگی به حافظه افراد را کم می‌کنند.

جمع‌بندی

یک فرآیند حرفه‌ای Troubleshooting باید بین مشاهده، فرضیه، تست و نتیجه مرز مشخص داشته باشد. هرچه شواهد بهتر ثبت شوند، تصمیم‌گیری سریع‌تر، ریسک تغییر کمتر و نتیجه قابل دفاع‌تر می‌شود.
